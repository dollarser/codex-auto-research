# Auto Research 设计原则

本文是 Auto Research 的最高层设计准则，用于判断需求和方案是否符合项目初衷。具体架构、
接口、状态流转和恢复步骤见
[Supervisor 方案文档](AUTO_RESEARCH_SUPERVISOR_SCHEDULER_DESIGN.md)。两者冲突时，应优先
修改具体方案；只有研究工作方式本身改变时才修改本文。

## 1. 核心目标

Auto Research 最核心的目标只有一个：

> Codex 启动实验并完成当前可做的工作后，可以暂停 Goal；Supervisor 独立等待实验终态，
> 再恢复 Goal，让 Codex 分析结果并继续研究。

实验启动不等于立即暂停。Codex 可以继续分析数据、检查代码、准备配置或设计后续实验；只有
当前工作确实只剩等待时才暂停。

## 2. 职责边界

### Codex 负责研究

Codex 是研究决策的唯一 owner，负责理解目标、分析证据、设计和提交实验、判断串并行、诊断
失败，并决定继续、等待、阻塞或完成。

### Supervisor 负责等待闭环

Supervisor 负责可靠执行和监控已经提交的实验，并在实验终态后恢复等待中的 Goal。为了保证
这一闭环，它还负责防止重复接管、永久失联和失控进程。

Supervisor 不是研究 Agent、策略引擎、资源调度器、配额调度器或审批系统。它不判断实验是否
值得做、指标是否足够好、是否应该并行，也不替 Codex 决定失败后的研究方向。

## 3. 最小充分控制

Auto Research 只系统性保证三件事：

1. **避免无限循环**：自动激活、恢复、重试或重启必须收敛。
2. **避免永久停滞**：已经提交的实验必须持续有人监控；实验终态后，等待中的 Goal 必须有
   可恢复路径。
3. **避免失控进程**：不能在进程仍可能存活时释放所有权，也不能让多个控制者同时接管同一
   Goal 或实验。

不属于这三类系统风险的判断原则上交给 Codex。不能仅为了防止一次不够理想的研究决策，给
Supervisor 增加策略限制或复杂状态机。

## 4. Goal 语义

Goal 的实时状态是唯一权威事实：

- `active`：Codex 正常研究，Supervisor 不干预；
- `paused`：Codex 正在等待，受管实验终态后恢复，不追溯暂停原因；
- `blocked`：存在真实阻塞，实验终态不自动解除；
- `complete`：研究目标结束，不重放旧目标；
- 无法自动处理的状态：停止自动推进，保留人工恢复路径。

Supervisor 不根据旧文本、旧标记或本地复制状态推测 Goal 状态。不同操作入口可以共存，但
必须读写同一权威事实，不能形成相互竞争的调度器或重复唤醒所有权。只读观察不属于第二套
控制面。

## 5. 实验与结果

- Codex 决定运行什么实验；Supervisor 不增加研究策略门槛。
- 实验、进程身份和终态必须持久化，不依赖某一轮 Codex 执行或临时连接存活。
- Codex 可以主动查询状态和读取完整结果；通知只是辅助，失败不能中断闭环。
- 成功、失败、超时、取消和丢失都是需要 Codex 分析的终态证据，对 Goal 恢复流程等价。
- 多实验串行或并行属于 Codex 的研究与资源决策，Supervisor 不设置固定数量策略。

## 6. 错误与恢复

- 可安全继续时继续，并保留足够的诊断证据。
- 自动恢复必须有明确边界，不能因为失败形成递归或后台循环。
- 自动修复失败可以等待人工处理，但不能停止对已经提交实验的监控和终态收尾。
- 只有无法确认进程安全、可能造成重复所有者、会永久丢失实验，或已经形成循环时才
  fail closed。
- 不得因为一次可容忍的通知、展示、查询或连接失败终止研究流程。

系统不追求跨进程严格 exactly-once。一次可收敛的重复通知或额外恢复动作可以接受；不得为
消除这种单次重复引入更复杂、更容易失控的状态机。

## 7. 简化与演进

- 只维护当前最优路径，不承担未明确要求的旧版本兼容成本。
- 每个持久字段都必须具有控制、恢复、诊断或审计价值，否则删除。
- 同一事实只有一个权威来源；可重建的信息不重复持久化。
- 新状态必须对应不同的恢复动作，纯展示阶段不应成为控制状态。
- 新限制、新重试和新标记默认不增加；必须证明其用于避免无限循环、永久停滞或失控进程。
- 在满足可靠闭环的前提下，让 Supervisor 尽可能少做决定，把研究自主权留给 Codex。

## 8. 设计评审清单

任何 Supervisor 变更合入前，应回答：

1. 是否直接改善“等待实验终态并恢复 Goal”的可靠性？
2. 防止的是无限循环、永久停滞还是失控进程？如果都不是，为什么不能交给 Codex？
3. 是否把研究、资源或指标决策从 Codex 转移给了 Supervisor？
4. 新增状态或持久字段是否真的对应不同恢复动作，且无法从权威事实重建？
5. 单次外部失败后，已经提交的实验是否仍能被监控和收尾？
6. 是否严格遵守实时 Goal 状态的语义？
7. 是否可能产生重复控制者、重复 Worker 或无人管理的进程？
8. 自动恢复是否有明确边界，并最终收敛？

满足清单不代表功能越多越好。最优方案是在完成可靠等待闭环的前提下，保持最少的系统控制。
